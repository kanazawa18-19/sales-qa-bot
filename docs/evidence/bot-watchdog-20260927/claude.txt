W1 起動直後の失敗による即時再起動ループ

根拠: Restartの条件 !cancelled() は、Install dependenciesが失敗して「Run bot」がskippedになった場合でも真になります。この場合、直ちにdispatchが実行され、次のrunも同じ理由で失敗する、という流れが1〜2分間隔で続きます。直列なので二重起動にはなりませんが、ループは止まりません。常にrunが存在するためwatchdogは介入できません。また、Restart自体は成功するので「再起動失敗を本人へ通知」も発火しません。PyPIの障害、トークンの失効、supervise直後の異常終了などで起こります。これは今回の変更以前からある問題ですが、自己再起動の範囲に含まれます。

最小修正: 自己再起動を正常終了時だけに限定します。それ以外の失敗は、watchdogの時計による間隔(約30分)で復旧させます。


yaml
      - name: Run bot
        id: bot
        ...
      - name: Restart workflow
        id: restart
        if: ${{ !cancelled() && steps.bot.outcome == 'success' }}
      - name: 再起動失敗を本人へ通知
        if: ${{ failure() && steps.restart.outcome != 'success' }}

前提として、superviseが24分の正常終了時にexit 0を返す必要があります。資料にはruntime_ops.pyがないため、確認が必要です。トレードオフとして、子プロセスのterminateが固まって27分のstep上限に達した場合も、復旧はwatchdog待ちになります。通知文言は「再起動失敗」のままでも運用上は問題ありません。

W2 停止手段がない

根拠: 実行中のrunを手動でcancelするとRestartはskipされますが、次の17分・47分の確認で「未完了runなし」と判定され、復旧要求が出されます。誤動作時の緊急停止が自動で打ち消されてしまいます。

最小修正: docに停止手順を追記します。コードの変更は不要です。

W3 scheduleの自動無効化

根拠: 公開リポジトリでは、60日間リポジトリ活動がないとscheduleが自動で無効化されます。Botの自己dispatchはリポジトリ活動として数えられません。安定稼働してコミットが止まると、watchdogが静かに止まり、自己再起動が一度途切れた時点でBotは復旧しなくなります。事前のメール警告は、cronを最後に編集した人に届く想定です。

最小修正: docに、定期的にwatchdogの最終実行日時を確認することを追記します。GAS優先の方針に沿った代替策として、GASの時間トリガーから bot-watchdog.yml をworkflow_dispatchする方法があります。bot.ymlを直接起動せず、判断はwatchdogに残せます。追加GCPは不要ですが、GitHubトークンをGASのスクリプトプロパティに保管する必要があるため、今回は任意とします。
